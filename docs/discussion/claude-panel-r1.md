## Survived issues
### [C2] major (merged as critical) — The gate depends on the request's tier, not on a mode: T0 'one bounded local edit' and I2's 'instruction to implement' allow writes with no plan
- lenses: logic, opus-fidelity, gpt-prompting, redteam
- quote: I2  Only an explicit user instruction to implement moves you into EXECUTE.
- problem: Claude Code Plan mode performs no edit of any size before approval. v4 is a 'plan when risky' policy instead. T0 includes 'one bounded local edit, trivially reversible' and sends it to 'Answer. No header, no stages, no ceremony', so the edit happens immediately. v4 never states the starting state; 'T1/T2는 기본 PLAN' appears only in Section 4, outside the prompt. I2 says any 'explicit user instruction to implement' enters EXECUTE, and an opening request such as 'add a nullable column' or 'fix the login bug' is literally that. I2 also has invariant precedence over <approval>, which is the only place that ties approval to a presented plan. A pre-approval ('계획 짜고 승인한 걸로 치고 구현까지 해') also matches I2. I1 bans only a 'full implementation', while <gate> bans any preview code, so partial snippets during PLAN are undefined.
- predicted behavior: Imperative first messages ('fix X', 'add Y', 'go fix the login bug') get read as the I2 trigger and edited right away, since approval_policy=never never prompts. One-line fixes are applied as T0 with no gate. Different runs of the same small request disagree on whether a plan is needed.
- proposed fix: Replace I2 with: "I2  You start every task in PLAN. Only approval of a plan you have already presented, given in a later user message (see <approval>), moves you into EXECUTE, and only for that plan's scope. A task request by itself ('add X', 'fix Y', 'just implement it') is a request to plan that work." Change T0 to read-only work only: "Factual lookup, explanation, or read-only investigation that changes nothing. Also: anything that is not software engineering work." Under T1 add: "Any file change, however small, is at least T1." A T1 plan for a one-line fix is short under OUTPUT B, so this adds little ceremony. Some lenses proposed keeping a T0 edit exception inside PLAN (logic). I prefer removing it: that is what the Opus behavior being copied does, and without a sandbox any exception becomes the attack surface (see C5).
- skeptic verdict: I read the whole target file (verified). The core of the issue holds, but several sub-claims are overstated, and "critical" is too high.

**What holds (verified by reading):**
- T0 at lines 112-116 says "one bounded local edit, trivially reversible" and routes it to "→ Answer. No header, no stages, no ceremony." No clause gates that edit. The tier matrix confirms it: "Approval gate - Y Y", so T0 has no gate.
- The prompt never states a starting mode. PLAN as the default appears only in Section 4 (line 491, "T1/T2는 기본 PLAN"), which is outside the fenced prompt.
- Because of that, T0 edits conflict with I1 ("PLAN never writes"). If the model assumes it starts in PLAN, the invariant forbids the T0 edit, but T0 has no gate or output defined for that case. If it assumes it does not start in PLAN, the edit goes through. So run-to-run disagreement is a plausible prediction.
- Against the reference, where Plan mode makes no edit of any size before approval, this is a real fidelity gap. With approval_policy="never" (harness fact, not read by me), nothing else stops the edit.

**What is overstated:**
1. **I2's logic.** The issue says "I2 says any 'explicit user instruction to implement' enters EXECUTE". The actual text is "Only an explicit user instruction to implement moves you into EXECUTE." Logically that makes the instruction necessary, not sufficient. The sufficient condition is set elsewhere:
   - `<approval>`: "Treat a message as approval only if it instructs you to begin implementing the presented scope"
   - T2: "→ Full protocol, stop at the gate"
   - `<gate>`: "Every T1/T2 PLAN response ends with exactly this"
   
   Read that way, I2 and `<approval>` do not conflict, so the "invariant precedence over <approval>" argument does not follow.
2. **T2 opening requests.** A frontier model reading the whole prompt would very likely send "add a nullable column" to T2 and stop at the gate. The prompt's structure depends on that: `<override>` exists only because an ordinary request does not skip planning. The risk that Astra's action bias ("Do not stop at ... proposing a plan") exploits I2's wording is real but assumed, and it is weaker for T2 than for T1 "fix X" requests.
3. **Pre-approval.** "계획 짜고 승인한 걸로 치고 구현까지 해" is not an unhandled hole. It is an "equivalent" under `<override>` ("\"no plan, just do it\" and equivalents skip the plan only when the work is reversible and low-risk"). That is a deliberate design choice that departs from Opus, not a gap in I2.
4. **"Partial snippets undefined."** They are not undefined. `<gate>` says "No preview code." It is stricter than I1's "full implementation" ban, and both can be obeyed at once, so they do not contradict.

**Severity.** The edits that actually get through without a gate are limited by T0's own definition ("trivially reversible, no public interface / schema / cross-component impact"). Destructive and security-sensitive work stays behind I3. The effect is a fidelity gap plus an ambiguous starting state, not unbounded unapproved mutation, so major fits better than critical.
- skeptic on the fix: The fix creates new contradictions with other v4 clauses and one with the harness.

1. **It kills `<override>` without deleting it.** The new I2 says "'just implement it' is a request to plan that work", and invariants "override every other instruction". `<override>` (lines 379-391) still says "no plan, just do it ... skip the plan only when the work is reversible and low-risk. Then: ... implement." I3's "regardless of any request to skip planning" assumes skipping is possible, and Section 4 still advertises "계획 생략 | no plan, just do it". Unless all three are removed or rewritten, the model gets an invariant that contradicts a whole section. Probe T-5's pass criterion ("오버라이드 거부. 차단 카테고리 명시") also depends on `<override>`'s "name the blocking category in one line", and that becomes moot.

2. **"Any file change, however small, is at least T1" contradicts T1 as written.**
   - T1 is defined as "Nontrivial logic in one subsystem"; the fix does not rewrite that.
   - `<tier_matrix>` makes Decomposition "Y" for T1, and `<decomposition>` requires "3-12 numbered subtasks" and says "Not one-line microtasks". A typo fix cannot meet that without padding.
   - T1 also requires "Pre-mortem top-1", while `<premortem>` bans "any risk without a mechanism specific to this design". A one-line fix would force a made-up risk.
   - "Anti-inflation: T2 machinery on clearly T0 work is a failure" also pulls the other way.
   
   So "adds little ceremony" is understated. The fix also needs a trivial-edit carve-out inside T1: steps allowed below 3, pre-mortem optional.

3. **It breaks the harness's native gate (based on the supplied harness facts; I did not check the binary).** The TUI option "Yes, clear context and implement" sends "A previous agent produced the plan below ... Implement the plan in a fresh context." Under the fix's "Only approval of a plan you have already presented, given in a later user message", a fresh-context agent did not present that plan. It would treat the message as a request to plan and re-plan instead of implementing. Plain "Implement the plan." after a mode switch is fine. The fresh-context path needs an explicit clause.

4. **"You start every task in PLAN" leaves "task" undefined.** Astra's template treats new messages as "steering the active task", so a follow-up tweak after EXECUTE ("also rename that") may or may not count as a new task. `<execute>`'s "Scope change" rule covers only architecture-level changes, so small follow-ups would again vary from run to run.

5. **It trades one contradiction for another with Astra's base prompt.** A gate on every edit strengthens the conflict with the base template's "Do not introduce unsolicited ... approval flows". That conflict comes with emulating Plan mode, but the fix should acknowledge it rather than claim low cost.

A smaller fix that avoids items 1-2:
- Add one sentence before `<triage>`: "You start in PLAN; T0 covers only read-only answers."
- Change T0's "one bounded local edit" to a T1 fast path ("single trivial edit: Steps may be 1, no pre-mortem").
- Keep I2 but reword it as a necessary condition tied to `<approval>`.
- Decide explicitly whether `<override>` survives, and update I3 and Section 4 to match.

- lenses: redteam, opus-fidelity, harness
- quote: create or edit files, run mutating commands, or emit a full implementation —
